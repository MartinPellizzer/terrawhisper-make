# 1.3 — An important database architecture decision

Do not create one table called `plants` containing a single scientific name and a list of synonyms.

That architecture will become a serious problem as your database grows.

Instead, I would start with the following entities:

### `taxa`

Represents taxonomic concepts as defined by a particular source.

| Column | Purpose |
|---|---|
| `taxon_id` | Your internal identifier |
| `rank` | Species, genus, family, etc. |
| `parent_taxon_id` | Internal parent |
| `taxonomic_status` | Accepted, synonym, unresolved, etc. |
| `created_at` | Record creation |
| `updated_at` | Last update |

### `scientific_names`

Stores scientific nomenclatural records.

| Column | Purpose |
|---|---|
| `name_id` | Internal identifier |
| `scientific_name` | Name string |
| `author_citation` | Botanical author |
| `publication_year` | Publication year |
| `basionym_id` | Related basionym |
| `ipni_id` | IPNI identifier, if available |

### `taxonomic_name_usage`

Connects names to taxonomic opinions.

| Column | Purpose |
|---|---|
| `usage_id` | Internal identifier |
| `name_id` | Scientific name |
| `taxon_id` | Taxon concept |
| `source_id` | Taxonomic source |
| `status` | Accepted, synonym, etc. |
| `accepted_name_id` | Accepted name according to source |

### `taxonomic_sources`

| Column | Purpose |
|---|---|
| `source_id` | Internal source identifier |
| `source_name` | WFO, COL, GBIF, etc. |
| `source_version` | Dataset version |
| `source_date` | Release date |
| `license` | License |
| `source_url` | Dataset URL |
| `citation` | Formal citation |

### `vernacular_names`

| Column | Purpose |
|---|---|
| `vernacular_id` | Internal identifier |
| `taxon_id` | Associated taxon |
| `name` | Common name |
| `language_code` | Language |
| `country_code` | Geographic context |
| `source_id` | Source |
| `source_reference` | Citation |

### `taxonomic_identifiers`

| Column | Purpose |
|---|---|
| `identifier_id` | Internal identifier |
| `taxon_id` | Your internal taxon |
| `identifier_type` | WFO, GBIF, COL, NCBI, etc. |
| `external_id` | External identifier |
| `source_version` | Version associated with ID |

This allows you to preserve taxonomic disagreements instead of accidentally overwriting them.

**Especially important:** WFO, COL, and GBIF identifiers are not interchangeable. Never assume that an identifier from one database can be used in another.

# 1.4 — The licensing issue you must solve from day one

Since you intend to publish your own website and database, there are two separate questions:

1. Can you download and use the data?
2. Can you redistribute the data, including in a public-facing database?

These are not always equivalent.

| Dataset | License / data-use situation |
|---|---|
| WFO Plant List | CC0; exceptionally permissive |
| GBIF Backbone | CC BY 4.0; attribution required |
| Catalogue of Life | Check release and constituent data conditions |
| IPNI | Verify applicable data-use terms |
| POWO | Verify individual dataset and content licensing |
| MPNS | Contact Kew for data supply and reuse terms |
| NCBI Taxonomy | Review NCBI data usage policies |
| ITIS | Review specific dataset and usage conditions |

For Kew datasets, the applicable license is specified in individual dataset metadata; Kew's general terms explain the conditions for using its resources. [Kew Gardens](https://www.kew.org/science/collections-and-resources/data-and-digital/terms-of-use?utm_source=chatgpt.com)

**I strongly recommend maintaining a license registry in your SQL database.** Every imported dataset should have a recorded license, attribution requirement, version, and redistribution status.
